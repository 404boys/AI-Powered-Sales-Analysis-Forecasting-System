## Dataset and validation design

- Dataset: cleaned Rossmann store sales data
- Expected input file: `Data/Cleaned/store_sales_cleaned.csv`
- Dataset dimensions and date coverage should be confirmed from the local file at training time.
- Model: LightGBM regressor trained on `log1p(Sales)`
- Validation: final 42 calendar days, held out chronologically; no random date split.

## Forecast protocol and limitations

This is a **one-day-ahead rolling validation**. For each validation date, lag features may use actual sales from earlier dates, including earlier dates within the validation window. This represents a workflow where actual sales become available before forecasting the next day.

It is **not** a fixed-origin 42-day forecast. A true multi-day forecast must generate future lag features recursively or use a separate horizon-aware design.

The cleaned input contains open, positive-sales rows only. For calendar lag construction, dates absent from a store's observed rows are treated as zero-sales history days. The source does not distinguish a closed day from an open day omitted because of zero sales, so this is an explicit assumption.

The model excludes `Customers`, `Sales`, and `Open` from predictors. Future customer counts are not known at forecast time. The What-If simulator holds historical lag features fixed and changes selected promotion/holiday inputs. Its output is a model scenario, not a causal estimate.

## Feature importance

The training script exports split-count feature importance to `artifacts/model/feature_importance.csv`. Add interpretation only after reviewing the generated file. Split-count importance measures how frequently a feature is used in tree splits; it does not establish causality or the direction of a feature's effect.

## Reproducibility

From the repository root:

```powershell
python -m pip install -r requirements.txt
python src/modeling/train_lightgbm.py
```

Generated model files are written to `artifacts/model/` locally and are not committed by default.
